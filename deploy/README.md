# Deploying on Kubernetes

`deploy/helm/aegis` is a Helm chart for the same services as
`docker-compose.yml`:

| Component | Image (Dockerfile target) | Port | Probes |
|---|---|---|---|
| `api-python` | `aegis/api-python` (FastAPI demo, model in-process) | 8000 | startup/liveness `/aegis/health`, readiness `/aegis/ready` |
| `api-node` | `aegis/api-node` (Express demo + status API) | 3000 | same |
| `ml` | `aegis/ml` (inference service) | 8001 | `/health` |
| `redis` | `redis:7-alpine`, no persistence | 6379 | `redis-cli ping` |
| `dashboard` | `aegis/dashboard` (nginx, unprivileged) | 8080 | `/` |

`/aegis/ready` returns 503 while Redis is unreachable. The pod then leaves the
Service, but is not restarted: liveness only checks the process.

## Install

The images are not published. Build them from the repository root, then
push them to your registry or load them into a local cluster:

```bash
for t in api-python api-node ml dashboard; do docker build --target $t -t aegis/$t:1.0.0 .; done
helm install aegis deploy/helm/aegis --set secret.secretKey=$(openssl rand -hex 32)
helm test aegis --logs          # probes, /aegis/metrics, telemetry -> token on both servers
```

To use a Secret you manage yourself, create one with the key
`AEGIS_SECRET_KEY` and pass `--set secret.existingSecret=<name>`. All replicas
need the same key: a token issued by one replica must verify on the others.

Without Helm, use the rendered defaults:

```bash
kubectl create secret generic aegis-secret --from-literal=AEGIS_SECRET_KEY=$(openssl rand -hex 32)
kubectl apply -f deploy/kubernetes/aegis.yaml
```

`deploy/kubernetes/aegis.yaml` is generated by `deploy/render-manifests.sh`.
CI checks that it matches the chart.

## What the chart sets up

- **State:**
  - Both API servers keep shared state in Redis (database 1 for Python, 0 for Node), so any number of replicas behave like one.
  - Without Redis (`redis.enabled=false` and no `externalUrl`), each replica has its own nonces, rate windows and sessions. Keep one replica then.
- **Metrics:**
  - `/aegis/metrics` on both API servers, with the same metric names (README, Monitoring).
  - Pods carry `prometheus.io/scrape|port|path` annotations.
  - `metrics.serviceMonitor.enabled=true` adds a ServiceMonitor for the Prometheus Operator.
- **Scaling:**
  - `autoscaling.enabled=true` adds a CPU-based HorizontalPodAutoscaler for each API server. It needs metrics-server.
  - A PodDisruptionBudget (`minAvailable: 1`) applies when there are several replicas.
- **Security:**
  - Non-root pods with a numeric UID, read-only root filesystem, no capabilities, RuntimeDefault seccomp.
  - The secret key is a Secret, and its checksum restarts the pods when it changes.
  - NetworkPolicies let only the API servers reach Redis and the ML service. The ML service's `/train` has no authentication. Enforcement depends on the cluster's CNI; it was not verified in the kind test (see below).
- **Ingress:** off by default. The status API under `/aegis/` (stats, events,
  GraphQL, live feed, metrics) describes your traffic, so put authentication in
  front of it before exposing it.

The memory limits follow the Phase F profile
(`docs/thesis/results/phase_f/memory_profile.md`). The in-process state of a
Node replica is bounded at ~250 MB with the default bounds.

## Test on kind

```bash
sh deploy/kind-test.sh     # builds, creates cluster "aegis", loads images, installs, runs helm test
```

### Sandboxed hosts

The chart was tested in a sandboxed container: Firecracker VM, cgroup v1, Docker inside. Plain `kind create cluster` failed
there for two reasons, neither of them caused by the chart, and a third limit applied:

1. **Negative `oom_score_adj` was not permitted.**
   - Kubernetes gives pause containers -998, and runc failed with "can't get final child's PID from pipe".
   - Fix: containerd's `restrict_oom_score_adj` option, in the kind config:

   ```yaml
   kind: Cluster
   apiVersion: kind.x-k8s.io/v1alpha4
   containerdConfigPatches:
   - |-
     [plugins."io.containerd.cri.v1.runtime"]
       restrict_oom_score_adj = true
   ```

2. **The kubelet did not start.**
   - The host has no `hugetlb` cgroup mount, so kind's entrypoint did not create `kubelet.slice` there.
   - Fix: create `/sys/fs/cgroup/hugetlb/kubelet.slice` in the node container, then run the kubeadm init and CNI steps by hand.
   - The exact commands:

   ```bash
   kind create cluster --name aegis --config kind.yaml --retain   # fails at kubeadm init
   docker exec aegis-control-plane sh -c 'mkdir -p /sys/fs/cgroup/hugetlb/kubelet.slice &&
     kubeadm reset -f && kubeadm init --config=/kind/kubeadm.conf --skip-token-print --ignore-preflight-errors=all'
   docker exec aegis-control-plane sed 's#{{ .PodSubnet }}#10.244.0.0/16#' /kind/manifests/default-cni.yaml | kubectl apply -f -
   docker exec aegis-control-plane cat /kind/manifests/default-storage.yaml | kubectl apply -f -
   ```

   (Before these, copy `/etc/kubernetes/admin.conf` from the node to your kubeconfig, using the published API port.)

3. **NetworkPolicies were not enforced.**
   - kindnet could not program nftables there, so the policies were accepted but had no effect.
   - Results: [`docs/thesis/results/phase_f/kubernetes.md`](../docs/thesis/results/phase_f/kubernetes.md).

On a normal Linux, macOS or Windows Docker host, none of this should be needed (not tested here).
